# PLAN00: フェーズの定義と安全契約を確定する

**状態**: 実施済み（ブランチ `docs/phase-and-safety-contract`）

## なぜやるか

「早く自動売買を動かしたい」という目的と、現在の [ロードマップ](../overview/roadmap.md) の記述が**正面から矛盾しています**。

- Phase3 の禁止事項: **「手動の承認なしで実際の注文を出すこと」**
- Phase3 の着手条件: **「Phase2の完了条件をすべて満たしている」**（＝LINE通知・Web画面・画面からの設定変更）

つまり現在の文書どおりに進めると、次のどちらかになります。

- Web画面と設定変更画面を作り終えるまで実注文に着手できない。
- 実注文をしても、毎回人間が承認するまで注文が出ない（＝無人の自動売買ではない）。

コードだけ直しても、この矛盾は消えません。**先に文書上の到達点を決めないと、以降の計画の完了条件が決められません。**

## ゴール

「どこまで行けば実資金を投入してよいか」「どこまで行けば人間の承認なしで動かしてよいか」が、数字と条件で書かれている。

## 決めること

### 1. Phase2 を分割するか

推奨: **Phase2a（通知・状態確認）と Phase2b（Web画面・設定変更）に分割し、Phase3 の着手条件を Phase2a の完了に変える。**

- 通知は安全運用に必須です。注文、約定、異常停止を人間が知れないまま実資金を動かすことはできません。
- Web画面と「画面からの設定変更」は実注文の必須条件ではありません。稼働確認はログ・通知・取引所の公式アプリで代替できます。設定変更画面は誤操作と認可の新しいリスクを増やします。
- **黙って飛ばさず、ロードマップを正式に書き換えてください。** 文書と実態がズレることが、[改善計画](../improvements/README.md) で最大の問題として洗い出された点です。

### 2. 手動承認を挟むか

**決定済み: 手動承認は実装しない。無人で運転し、安全は「金額の上限」と「自動停止」で担保する。**（オーナー判断 / 2026-08-29）

この決定により、[ロードマップ](../overview/roadmap.md) の Phase3 禁止事項**「手動の承認なしで実際の注文を出すこと」を正式に書き換える必要があります。** 黙って破らないでください。書き換えるときは、承認の代わりに何が安全を担保するのかを同じ文書に明記します。

承認が無い分、**次の3つが承認の代替として機能しなければなりません。ここが弱いまま無人運転に入ると、歯止めが1つも無くなります。**

1. **口座に入れる金額の上限**。最も確実な防御です。口座に入っていないお金は失えません。
2. **自動で止まる条件**（1日の損失上限、連敗停止、スリッページ上限、API異常）。人間が止めるのではなく、システムが自分で止まります。
3. **通知と緊急停止**。止まったこと・異常なことに気づき、すぐ止められること。

承認を外す代わりに、この3つの実装は**必須**です。「後で入れる」にはできません。

### 3. 安全ルールの数字を確定する

現在の [config/application-gmo.yaml](../../config/application-gmo.yaml) の値は、実運用を想定した数字になっていません（`max_order_jpy: 1000` は BTC の最小注文数量を満たせない可能性があります。[PLAN02](plan02-order-safety-guards.md) の A 参照）。

決めるもの:

**決定済み。数値の正は [ロードマップ](../overview/roadmap.md) の「安全ルール（数値）」です。** ここに書き写さないでください。

| 項目 | 決定値 | 実装 |
| --- | --- | --- |
| 1回の注文額上限 | 10,000円 | 実装済み（`max_order_jpy`） |
| 1日の注文額上限 | 20,000円 | 実装済み（`max_daily_order_jpy`） |
| 保有額上限 | 10,000円 | 実装済み（`max_position_jpy`） |
| 1日の損失上限 | 2,000円 | **未実装** → [PLAN03](plan03-notification.md) |
| 連敗による停止 | 3連敗 | **未実装** → [PLAN03](plan03-notification.md) |
| 許容スリッページ | 0.5% | **未実装** → [PLAN02](plan02-order-safety-guards.md) / [PLAN03](plan03-notification.md) |
| 実取引で許可する Strategy | `SafeReboundStrategy` のみ | 設定にコメントで明記。強制は [PLAN02](plan02-order-safety-guards.md) の fail-fast |
| 実取引で許可する `order_sizing_mode` | `FIXED_AMOUNT` のみ | 同上 |
| 口座に入れる金額 | 30,000円 | 設定ではなく運用。[PLAN05](plan05-canary-with-real-money.md) の着手条件 |
| 取引口座 | 専用口座（サブ口座）を推奨 | 使わない場合は他の BTC をその口座に置かない |
| 専用口座を使うか | 未定 | ボット以外の資産と混ぜない（[PLAN01](plan01-real-sell-order.md) の論点4） |

**「損失上限」「連敗停止」「スリッページ上限」は数値が決まっただけで、実装は1つもありません。** 手動承認を置かない方針を取った以上、**これらは実注文を有効にする前に必ず実装してください。** 実装しないまま `real_trade_enabled: true` にすることは、ロードマップの Phase3 禁止事項に違反します。

### 4. 緊急停止（kill switch）の手段

**決定済み: Cloud Scheduler の停止と設定フラグを正とする。**（オーナー判断 / 2026-08-29）

手順は [ロードマップ](../overview/roadmap.md) の「緊急停止（kill switch）」に記載しました。既存の [scheduler-gcp.yml](../../.github/workflows/scheduler-gcp.yml) に `pause` があるため、追加の実装は不要です。

**注意: Scheduler を止めても、すでに保有しているポジションはそのまま残ります。** 決済は取引所の画面から手動で行います。急いで損失を止めたい場合は、Scheduler の停止と並行して手動決済してください。

**実資金を入れる前に、実際に一度試して止まることを確認してください**（[PLAN05](plan05-canary-with-real-money.md) の着手条件）。

## 受け入れ条件

- ロードマップの Phase2 / Phase3 の着手条件・完了条件・禁止事項が、上の決定を反映して書き換わっている。特に「手動の承認なしで実際の注文を出すこと」の扱いが、代替する安全ルールとセットで書かれている。
- 安全ルールの数字がすべて埋まっている（「後で決める」が残っていない）。
- 緊急停止の手順が書かれており、実際に試せる形になっている。
- **Kotlin コードは変更しない。** Phase1 の禁止事項（実注文をしない）は維持されたまま。`config/application-gmo.yaml` の上限値のみ、決定した数値に更新する（`real_trade_enabled: false` のため挙動は変わらない）。

```bash
./gradlew build
```

あわせて文書のリンク切れが無いことを確認してください。
