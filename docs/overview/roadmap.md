# ロードマップ（Phaseごとの着手・完了条件）

## 文書の目的

- 各Phase（開発の段階）の完了条件と着手条件
- まだ解決していないリスク（ビジネス・技術）
- 各フェーズで「やってはいけないこと（禁止事項）」
- 将来的な展開の候補

## 対象読者

プロジェクト管理者、開発メンバー

## 関連ドキュメント

[product.md](product.md)

## 概要

この文書は、各Phaseを「着手条件」「完了条件」「未解決リスク」「禁止事項」の4つの項目で管理するための基準です。現在は Phase1（シミュレーション環境）を進めています。

## Phase1（安全なシミュレーション基盤）

### 着手条件（始めるために必要なこと）

- フォルダ構成などの方針が決まっている。
- 開発環境（Dockerなど）が使える状態になっている。
- 最小限の要件（GMOコイン、BTC、ローカル実行）が明確になっている。

### 完了条件（終わったと言える状態）

- GMOコインから価格データが取得できる。
- 5分ごとに売買の判定ができる。
- 結果をJSONやCSVで保存できる。
- 手元のパソコンやDocker、GitHub Actions、GCP上でプログラムが動く。

### 未解決リスク（まだ心配なこと）

- APIの仕様が変わったときに直す手間がどのくらいかかるか分からない。
- 長時間動かしたときに、メモリやログがいっぱいにならないか確認できていない。
- 相場が急変したときに、売買ルールが正しく動くか分からない。

### 禁止事項（やってはいけないこと）

- **実際の注文を送ること**
- 実資金を入れること
- 本物の自動売買ボットとして動かすこと

## Phase2a（通知と自動停止）

Phase2 は Phase2a と Phase2b に分割しました。**Phase3 の着手条件は Phase2a の完了までです。** Web画面（Phase2b）は実注文の前提条件から外しました。稼働確認は通知・ログ・取引所の公式アプリで代替でき、設定変更画面は誤操作と認可の新しいリスクを増やすためです。

### 着手条件

- Phase1の完了条件をすべて満たしている。
- 通知の送信先（LINE、Discord など）が決まっている。

### 完了条件

- 「売買サイン・理由・現在価格・想定損益」を通知できる。
- 実注文の送信、約定、安全チェックによる見送り、異常停止を通知できる。
- 定期実行が生きていることを知らせる通知（heartbeat）が届く。
- 下記「安全ルール」の自動停止が実装され、発動すると通知が届く。
- 通知本文に秘密情報が含まれない。

### 未解決リスク

- 通知が遅れたり届かなかったりしたときの対策が決まっていない。
- ジョブが起動しなくなった場合、通知は「来ない」だけなので沈黙として現れる。外部からの監視は Phase4 で扱う。

### 禁止事項

- 自動で実際の注文を出すこと。
- 通知にAPIキーなどの秘密情報を含めること。

## Phase2b（Web画面）

**Phase3 の前提条件ではありません。** Phase3 以降に必要になった時点で着手します。

### 着手条件

- Phase2a の完了条件をすべて満たしている。

### 完了条件

- Web画面からアプリが動いているか確認できる。
- 画面から設定を変更できる。

### 未解決リスク

- 画面操作を間違えたときの防止策が足りない。

### 禁止事項

- 画面からAPIキーなどの秘密情報をそのまま保存すること。

## Phase3（実注文 + 安全制御）

### 先行実装済みの範囲

Phase3 のスコープのうち、次はすでにコードに存在します。ただし **Phase1 では起動時ガードにより実行できません**（`app.phase` が 3 未満だと、実注文が有効な設定を検出した時点で異常終了します）。Phase1/Phase2 の禁止事項と矛盾しないのはこのためです。

- 実装済み: GMOコイン Private API クライアント、署名生成、実注文前の安全チェック（`RealTradingSafetyChecker`）、買い注文と売り注文の送信・約定確認
- 実装済み（追加分）: 注文数量の刻みへの丸め、注文価格の Ticker 基準化、手数料を含む上限判定、市場データの検証、API のリトライとタイムアウト、重複実行の抑止、損失上限・連敗停止・スリッページ上限、通知
- 未実装: 日次サマリーの通知、沈黙の検知（外部監視）、本番環境での実 API 疎通確認

実注文を有効にするまでに必要な作業と順序は [実注文までの作業計画](../plans/README.md) にあります。

詳細は [リアル購入処理（GMOコイン） 仕様書](../specifications/features/real-trading-gmo-order.md) を参照してください。

### 手動承認を置かない決定

**このフェーズでは手動の承認を挟みません。無人で運転し、安全は「金額の上限」と「システムが自分で止まること」で担保します。**（オーナー判断 / 2026-08-29）

以前この文書は Phase3 の禁止事項として「手動の承認なしで実際の注文を出すこと」を挙げていました。承認を挟むと、承認が遅れて売買のタイミングを逃す上に、無人の自動売買という目的に到達しません。承認を外す代わりに、下記の安全ルールを**すべて実装してから**実注文を有効にします。承認の代替なので、1つでも欠けたら実注文は有効にできません。

### 安全ルール（数値）

実注文を有効にする条件です。金額は「全額失っても困らない額」として決めています。

| 項目 | 設定キー | 値 |
| --- | --- | --- |
| 1回の注文額上限 | `max_order_jpy` | 10,000円 |
| 1日の注文額上限 | `max_daily_order_jpy` | 20,000円 |
| 保有額上限 | `max_position_jpy` | 10,000円 |
| 1日の損失上限 | `max_daily_loss_jpy` | 2,000円 |
| 連敗による停止 | `max_consecutive_losses` | 3連敗 |
| 許容スリッページ | 未実装 | 0.5% |
| 口座に入れる金額 | （設定ではない） | 30,000円 |

- **「口座に入れる金額」が最後の防御線です。** 口座に入っていないお金は失えません。上限値の実装に不具合があっても、これだけは効きます。
- 「1日の損失上限」「連敗による停止」「許容スリッページ」は実装済みです。**いずれもその日のうちは新規の買いを止め、日付が変われば自動で解除されます。** 解除されないと、停止したまま売買が行われず、連敗が途切れる機会も無くなって永久に止まったままになります。
- いずれの停止も**止めるのは新規の買いだけ**です。保有を解消する売りは止めません。停止中に売りまで止めると、ポジションを抱えたまま損切りできなくなるためです。

### 実取引で許可する設定

安全側に倒すため、実取引では次に限定します。

| 項目 | 許可する値 | 理由 |
| --- | --- | --- |
| `trading.strategy_name` | `SafeReboundStrategy` のみ | クールダウンを使う Strategy は、実注文の売りで `lastStopLossTime` を更新しないためクールダウンが機能しない |
| `trading.order_sizing_mode` | `FIXED_AMOUNT` のみ | `ALL_IN` は1回の露出が読めない |

### 取引口座

**このアプリ専用の口座（またはサブ口座）を使うことを推奨します。** 同じ口座に他の用途の資産があると、状態の突き合わせが複雑になります。専用口座を使わない場合は、**その口座に他の BTC を置かないでください**。

### 緊急停止（kill switch）

止める手順は次です。**実資金を入れる前に、実際に一度試して止まることを確認してください。**

1. **Cloud Scheduler を停止する**（[scheduler-gcp.yml](https://github.com/ht-0328/crypto-autotrading-lab/blob/main/.github/workflows/scheduler-gcp.yml) の `pause`）。新規の実行が止まります。ここまでで新しい注文は出なくなります。
2. **`real_trade_enabled: false` に戻して再デプロイする。** 実行が再開されても注文が出ない状態に戻します。
3. **保有しているポジションの決済は、取引所の画面から手動で行います。** アプリは停止済みなので売りません。

手順1だけでは、すでに保有しているポジションはそのまま残ります。急いで損失を止めたい場合は、手順1と並行して手順3を行ってください。

### 着手条件

- Phase2a の完了条件をすべて満たしている。
- 上記の安全ルールの数値が決まっている。
- 緊急停止の手順を実際に試し、止まることを確認済み。

### 完了条件

- 実注文の買いと売りが、人手を介さず本番環境で1サイクル完結する。
- 安全ルール（損切り、1日の損失上限、連敗停止、スリッページ上限）が確実に動く。
- 取引所の記録、`state.json`、通知の3つが一致している。
- 上限値を超える注文が1回も出ていない。

### 未解決リスク

- 相場が急変したときに、想定通りに買えない/売れないリスク。
- 5分間隔・API停止中・朝6時前後は、アプリ側の損切りが動かない。この空白時間の損失は、投入額で管理するしかない。
- 手動承認を置かないため、発注の直前に人間が内容を見るタイミングが無い。異常の把握は事後の通知に依存する。

### 禁止事項

- 安全ルールをオフにしたまま注文を許可すること。
- 安全ルールが1つでも未実装のまま実注文を有効にすること。
- 上記「実取引で許可する設定」以外の Strategy・`order_sizing_mode` で実注文を行うこと。

## Phase4（連続運転と上限の引き上げ）

Phase3 は「人が見ている時間に手動で実行し、最小額で1サイクルを通す」ところまでです。Phase4 で定期実行に戻し、人が見ていない時間も含めて回し続けます。

### 着手条件

- Phase3 で、不整合ゼロの売買サイクルが規定回数連続で成立している。
- 想定外の停止が規定日数ゼロ。
- 通知・heartbeat・緊急停止が実際に機能したことを確認済み。

### 完了条件

- 定期実行で一定期間回り続け、取引所の記録・`state.json`・通知が一致し続けている。
- ジョブが起動しなくなった場合に、外部の監視で気づける。

### 未解決リスク

- 人が見ていない時間に出た不整合は、気づいたときには損失が確定している。

### 禁止事項

- 実績を確認せずに上限額を引き上げること。

## 用語補足

- **Entry / Exit Criteria**: 着手条件と完了条件のこと。
- **ロールバック**: 問題が起きたときに、元の安全な状態に戻すこと。
- **フェイルセーフ**: 障害が起きたときに、安全な側に倒してシステムを止める仕組み。
