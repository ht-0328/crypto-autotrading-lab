## アプリケーションの目的

- このアプリは、いきなり実資金で売買するためのものではありません。
- まずは安全に検証するためのアプリです。
- 自動売買ロジックの検証サイクルを迅速に回せる実行基盤を確立します。
- シミュレーションの検証結果を後から確認できるように記録し、将来的に実資金を投入するかどうかの判断材料を集めます。
- 設定変更や障害からの復旧をすばやく行えるようにし、運用の手間を減らします。

## 基本方針

- **安全性を最優先**にします。
- データが足りない、APIが失敗した、時刻がズレているなど、危ない状態では売買判断を見送ります。
- 後から原因を確認できるように、ログやCSVに結果をしっかり残します。

## Phase1の対象範囲

- シミュレーション環境での稼働。
- 安全に売買ロジックの検証を行うための基盤構築。

## Phase1の対象外

- 実際の資金を使った売買。
- プライベートAPIを使った注文処理など。

## Phase1の完了条件

実装や検証として明確に確認できる以下の項目を完了条件とします。

- Public APIから価格データを正常に取得できること
- `SafeReboundStrategy` などのロジックで「買い」「売り」「見送り」の判定ができること
- 判定結果や実行記録をログおよびCSVファイルに保存できること
- API通信の失敗時やデータ不足時に、無理な売買判断をせず安全に見送れること
- 秘密情報（APIキーなど）をソースコード、ログ、CSVに出力しないこと
- GitHub ActionsのCIでテストが正常に成功すること

## 将来的に確認する指標

シミュレーション結果が十分に蓄積された後に、以下の指標（KPI）を確認します。

- **月次最大ドローダウン**: シミュレーション上の資産額を基準に、最大の資産減少率が -10% 以内に収まっているか
- **システム稼働率**: 定期実行Jobとして設定されたスケジュール通りに正常終了した割合（目標: 99.0% 以上）
- **誤判定率**: 取得したデータに対して、意図したロジック通りの判定（正解）と異なる結果が出た割合（目標: 1.0% 未満）
- **データ保存成功率**: 実行ごとの状態や履歴が、エラーで欠損することなくCSVや状態ファイルに保存できた割合（目標: 99.9% 以上）

## 安全設計

- 重複して実行された場合は、二重に保存・更新しないようにスキップします。
- システムの時刻と市場データの時刻にズレがある場合（例: ±60秒以上）、警告を出します。ズレが続く場合は売買を止めて見送りにします。

### 実注文の安全ルール（Phase3以降）

実資金を動かすフェーズでは、手動の承認を挟まず無人で運転します。承認の代わりに次で安全を担保します。**具体的な数値は [ロードマップ](roadmap.md) の「安全ルール（数値）」を正とします。** ここに数値を書き写さないでください。

- **金額の上限**: 1回の注文額、1日の注文額、保有額に上限を設けます。
- **口座に入れる金額の上限**: 最後の防御線です。口座に入っていないお金は失えません。上限値の実装に不具合があっても、これだけは効きます。
- **自動で止まる条件**: 1日の損失上限、連敗、想定からのスリッページ、API異常。いずれかに達したらシステムが自分で新規の買いを止めます。
- **止めるのは新規の買いだけ**: 保有を解消する売りは止めません。停止中に売りまで止めると、ポジションを抱えたまま損切りできなくなります。
- **通知**: 注文、約定、見送り、停止を人間に伝えます。無人運転では、異常の把握が事後の通知だけに依存します。

### 緊急停止

人間がすぐ売買を止める手段です。手順は [ロードマップ](roadmap.md) の「緊急停止（kill switch）」を参照してください。実資金を入れる前に、実際に一度試して止まることを確認します。

## 異常時の動作

- **API通信に失敗した場合**:
  - すぐに諦めず、少しずつ間隔を空けながら最大3回まで再試行します（指数バックオフ）。
  - それでも失敗した場合は、今回の実行は「失敗」としてエラーを出します。
  - 失敗している間は、無理に売買判断を行わず、状態の更新もしません。
- **データが足りない場合**:
  - 判断に必要なデータ（過去の価格など）が足りないときは、安全を優先して「見送り」にします。
  - 足りないデータがあることは警告としてログに残します。
- **実注文の処理中に例外が発生した場合（Phase3以降）**:
  - 新規の買いを止めます（`state.json` の `realTrading.isStopped` を `true` にします）。
  - 復旧は自動では行いません。人が状況を確認して手動で戻します（[復旧手順](../operations/real-trading-recovery.md)）。
  - **保有を解消する売りは止めません。** 停止中に売りまで止めると、損切りできなくなるためです。

## 記録方針

- 後から何が起きたか分かるように（可観測性）、以下の情報をログに出します。
  - 実行の開始時刻と終了時刻
  - 取得したデータの件数
  - 判定された売買サイン（買い・売り・見送り・保有中など）
  - データの保存結果
  - エラーが起きた場合は、その種類と原因
- ログは「情報」「警告」「エラー」などを区別して出力します。

## 秘密情報の管理方針

- APIキー、APIシークレット、認証トークンなどの秘密情報は、ソースコードの中に直接書いたり、Gitの管理（コミット）に入れたりしてはいけません。
- これらの秘密情報は、環境変数などを使って外からアプリに渡します。
- ログやCSVなどの出力には、秘密情報が出ないように隠します（マスキング）。
- 権限は必要最小限に設定します。

## 用語補足

- **KPI**: 目標として確認する数値
- **非機能要件**: 「どう動くか（機能）」ではなく「どのくらい速いか、安全か」といったシステムの性質
- **可観測性**: あとからシステムに何が起きたか確認できるようにすること
- **RTO**: 障害からどのくらいの時間で復旧したいかの目標
- **ドローダウン**: 資産が一番多かった時から、どれくらい減ったかを表す割合
- **指数バックオフ**: エラーが起きたとき、再試行するまでの待ち時間を「1秒、2秒、4秒…」と段々長くしていく仕組み
- **マスキング**: 秘密情報をログなどに出さないよう隠すこと
- **最小権限**: アプリが動くために必要な権限だけを与え、余分な権限は持たせないこと
- **ローテーション**: パスワードや鍵を定期的に新しいものに変更すること
- **フォールバック**: 異常が起きたときに、安全な別の方法に切り替えること
- **ステート**: アプリの「今の状態」（例: 今仮想通貨を持っているかどうか）
- **I/O**: 入力と出力（データの読み書きなど）
- **実行サイクル**: アプリが1回動いてから終わるまでの一連の処理の流れ
