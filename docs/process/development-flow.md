# 開発フロー（日次固定）

本ドキュメントは、日次で繰り返す標準フローを固定するための手順です。

## 0. 前提

* 1日の作業は原則「小さな変更を確実にマージする」ことを優先する
* すべての作業はIssue/Backlog起点で実施し、口頭依頼のみで進めない
* 変更は必ずPR経由で統合する（直push禁止）

## 1. Backlog整備

### 実施内容

* 未着手タスクを「目的・完了条件・優先度」で再整理する
* 本日の対象タスクを最大1〜3件に絞る
* 各タスクに受け入れ条件（テスト観点含む）を明記する

### 完了条件

* 今日着手するタスクが明確である
* Doneの定義が曖昧でない

## 2. AI依頼

### 実施内容

* 1タスクずつ、入力（背景・制約・期待成果）を明示して依頼する
* 生成結果は鵜呑みにせず、差分・副作用・セキュリティ観点を確認する
* 必要に応じて追加指示（修正依頼）を出す

### 完了条件

* 変更意図が説明できる状態で差分が作成されている
* ローカルで最低限の検証が完了している

## 3. PRレビュー

### 実施内容

* PRテンプレートに「目的・変更点・確認方法・リスク」を記載する
* レビュー観点を固定する
  * 仕様適合性
  * 安全性（誤発注・秘密情報漏えい）
  * 可読性 / 保守性
  * テスト妥当性
* 指摘はコメントで記録し、解決履歴を残す

### 完了条件

* 必須指摘が0件
* CI（またはローカル代替チェック）が通過

## 4. マージ

### 実施内容

* 承認済みPRのみマージする
* マージ方式（squash/rebase）をチーム方針に統一する
* マージ後に関連Issue/Backlogを更新する

### 完了条件

* main（または既定ブランチ）が壊れていない
* 追跡情報（PR、Issue、変更履歴）が紐づいている

## 5. リリース判定

### 実施内容

* 当日のマージ内容がリリース可能かを判定する
* 判定基準
  * ユーザー影響の有無
  * リスク増加の有無
  * ロールバック容易性
* リリースしない場合も「見送り理由」を残す

### 完了条件

* 「リリースする / しない」の判断が記録されている
* 次営業日の優先課題が明確になっている

* [ ] PRレビューで必須指摘を解消した
* [ ] マージ後の整合性を確認した
* [ ] リリース判定を記録した
