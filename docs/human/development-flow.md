# 開発フロー（日次固定）

本ドキュメントは、チームでの日次開発フローの標準手順です。

## 0. 前提方針

* 1日の作業は「小さな変更を確実にマージする」ことを優先して進めます。
* 作業は必ずIssueやBacklogを起点とし、タスク化されていない口頭依頼のみでの開発は避けます。
* mainブランチへの直接のPushは禁止し、必ずPull Request (PR) 経由で統合を行います。

## 1. Backlogの整備

### 実施内容
* 未着手タスクの「目的・完了条件・優先度」を明確にし、リストを再整理します。
* その日の作業対象タスクを最大1〜3件程度に絞り込みます。
* 各タスクには、テスト観点を含めた明確な受け入れ条件（Doneの定義）を明記します。

### 完了条件
* 本日着手するタスクと、その完了条件が誰が見ても明確になっていること。

## 2. タスクの実施（実装・検証）

### 実施内容
* タスクごとに背景や制約、期待される成果を確認しながら実装を進めます。
* コード変更後は、意図しない副作用が生じていないか、セキュリティ上の懸念がないかを確認します。
* ローカル環境でのテスト・動作確認を行います。

### 完了条件
* 変更の意図が明確に説明できる状態の差分が作成されていること。
* ローカル環境で最低限の動作検証が完了していること。

## 3. Pull Request (PR) とコードレビュー

### 実施内容
* PRを作成し、テンプレートに従って「目的・変更点・確認方法・リスク」を明記します。
* 以下の観点でレビューを実施します。
  * 仕様への適合性
  * 安全性（誤発注の防止、秘密情報漏洩の防止など）
  * コードの可読性と保守性
  * テストの妥当性とカバレッジ
* レビューでの指摘はコメントとして記録し、修正の履歴を残します。

### 完了条件
* レビューでの必須指摘事項がすべて解消されていること。
* CI（自動テスト）またはローカルでの代替テストがすべて通過していること。

## 4. マージの実施

### 実施内容
* 承認済みのPRのみをマージします。
* マージ方針（squashまたはrebase等）はチームのルールに従って統一します。
* マージ後は、関連するIssueやBacklogのステータスを更新します。

### 完了条件
* マージ後もmain（または既定）ブランチのビルドやテストが壊れていないこと。
* 変更履歴がIssueやPRと適切に紐付いて追跡可能であること。

## 5. リリースの判定

### 実施内容
* その日マージされた変更が本番環境へリリース可能かを判定します。
* 判定の際は、ユーザー影響の有無、リスクの増加、ロールバックの容易さを基準とします。
* リリースを見送る場合は、その理由を必ず記録します。

### 完了条件
* 当日の変更について「リリースする / しない」の判断が明確に記録されていること。
* 翌営業日に優先して取り組むべき課題が明確になっていること。
