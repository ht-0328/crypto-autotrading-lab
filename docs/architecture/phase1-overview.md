## まず結論
Phase1は、安全を最優先とし、実資金による実際の注文を行わない「シミュレーション環境」を作るフェーズです。

## Phase1 のルールとやること

- **対象取引所**: GMOコイン
- **対象通貨**: BTC（ビットコイン）
- **利用API**: 誰でも使える Public API だけを使います。
- **実行環境**: ローカルのDocker環境で動かせるようにします。
- **開発環境**: VS Code の devcontainer を使って開発できるようにします。
- **主な機能**:
  - 現在の価格や過去の価格データ（K線/ローソク足）を取得します。
  - 取得したデータをもとに、「買い」「売り」などの判定を行い、画面に出します。
  - 判定結果や価格の履歴をCSVファイルで保存します。
  - 今仮想通貨を持っているかどうか（ステート）をJSONファイルに保存します。

## フォルダ（ディレクトリ）のルール

アプリケーションのコードは `projects/crypto-autotrading-app/` にまとめ、他の設定ファイルと分けます。

```text
.
├─ config/                    # アプリの設定ファイルを入れる場所
├─ data/                      # 実行結果(CSV)や状態(JSON)を保存する場所
├─ docs/                      # ドキュメント群
├─ projects/
│  └─ crypto-autotrading-app/ # アプリの本体のコード
└─ README.md
```

## プログラムの構造（パッケージ）のルール

プログラムは役割ごとにフォルダ（パッケージ）を分けています。

- **`presentation`**: プログラムの入り口です。
- **`application`**: 5分ごとの定期実行の流れを管理します。
- **`domain.strategy`**: 「いつ買うか」「いつ売るか」のルール（売買判定）を書く場所です。
- **`domain.simulation`**: 仮想の資金や、今持っているかどうかの状態を管理します。
- **`infrastructure`**: APIとの通信や、ファイルの保存などを担当します。

**重要なルール（アーキテクチャ制約）**:
`domain` パッケージの中では、直接APIを叩いたり、ファイルを保存したりしてはいけません。外部とのやりとりはすべて `infrastructure` に任せます。

## プログラムが動く流れ（実行フロー）

Phase1 では、プログラムは5分ごとに以下の順番で動きます。

1. 設定ファイル（YAML）を読み込む。
2. GMOコインから最新の価格データを取得する。
3. 価格データをもとに、売買の判定ルールを実行する。
4. 判定結果に合わせて、シミュレーションの状態（仮想資金や保有ポジション）を更新する。
5. 実行結果を画面（コンソール）に出す。
6. 今回の結果をCSVに書き足し、最新の状態をJSONファイルに保存する。

## 売買の基本設定

売買のルールは [trading-logic.md](trading-logic.md) で詳しく説明しています。Phase1では本当の注文はしません。

- **初期仮想元本**: 10,000円
- **1回の売買金額**: 1,000円固定
- **ポジション上限**: 同時に持てるのは1つ（1ポジション）だけです。

## データの保存について

- **CSV出力**: 1日1ファイル作成し、日時のほかに価格、判定理由、仮想損益などを保存します。
- **JSON出力**: 今仮想通貨を持っているか、いくらで買ったかなどの最新状態を保存します。
- **設定ファイル（YAML）**: 毎回読み直すため、プログラムを再起動しなくても設定の変更が反映されます。

## 難しい言葉の説明
- **K線（ローソク足）**: 一定時間の「始まりの値段」「一番高い値段」「一番安い値段」「終わりの値段」をまとめたデータ。
- **ステート**: アプリの「今の状態」。
- **アーキテクチャ**: システム全体の構造や設計ルールのこと。
