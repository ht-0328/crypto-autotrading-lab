# プロダクト要求仕様（共通）

## 目的 / KPI

本ドキュメントは、`crypto-autotrading-lab` 全体で共通となるプロダクト要求（目的・運用品質・失敗時挙動・セキュリティ境界）を定義する。

### 目的

* 安全性を最優先しながら、自動売買ロジックの検証サイクルを短く回せる実行基盤を確立する。
* 検証結果を再現可能な形で蓄積し、将来フェーズの実運用判断に必要な根拠を残す。
* 設定変更や障害復旧にかかる時間を短縮し、運用負荷を抑えた継続改善を可能にする。

### KPI（Phase1 の初期目標）

* 月次最大ドローダウン（Max DD）: **-10% 以内**
* 稼働率（予定実行に対する成功実行の割合）: **99.0% 以上**
* 誤判定率（期待した売買判定との乖離率）: **1.0% 未満**
* データ保存成功率（CSV / state 保存の成功割合）: **99.9% 以上**

> 注: KPI はプロジェクトの進行に合わせて見直す。閾値変更時は本ドキュメントを更新し、各フェーズ仕様から参照する。

## 非機能要件

### 可観測性

* 各実行サイクルで、少なくとも以下をログに出力する。
  * 実行開始・終了時刻
  * データ取得件数
  * 売買判定結果
  * 保存結果（CSV / 状態ファイル）
  * 異常発生時のエラー種別と原因
* 正常系ログと異常系ログを判別できるログレベルを使用する（INFO / WARN / ERROR）。
* 1 実行単位を追跡できる識別子（実行IDまたは時刻）をログに含める。

### 復旧時間（RTO）

* 一時的障害（API疎通失敗・短時間のI/Oエラー）からの自動復旧: **15分以内**
* 手動介入が必要な障害の復旧目標: **60分以内**

### 設定変更反映時間

* 設定ファイル変更は、アプリの次回実行サイクルで反映されること。
* 反映までの最大時間目標: **5分以内**（定期実行間隔に依存）

### ログ保持

* アプリケーションログの保持期間: **30日以上**
* 集計・検証の基礎となるCSVおよび状態ファイルは、明示的な削除運用が決まるまで保持する。
* ログ・出力先は運用環境（ローカル / Docker）で一貫して参照可能であること。

## 失敗時仕様

### API失敗

* API呼び出し失敗時は指数バックオフを伴うリトライを最大3回実施する。
* 3回連続失敗した場合、その実行サイクルを失敗として終了し ERROR ログを出力する。
* API失敗中は売買判定を行わず、状態更新をスキップする。

### データ欠損

* 取得した価格データが必要本数に満たない場合は、売買判定を `見送り` とする。
* データ欠損時は欠損項目と不足件数を WARN ログに記録する。
* データ欠損が連続する場合は運用者が検知できるよう、一定回数ごとに ERROR を昇格出力する。

### 重複実行

* 同一対象時刻の実行が重複した場合、後続実行は副作用（保存・状態更新）を行わずスキップする。
* 重複判定のため、実行単位で一意キー（対象足時刻など）を使用する。

### 時刻ズレ

* システム時刻と市場データ時刻のズレを監視し、許容値（例: ±60秒）を超えた場合は WARN を出力する。
* 許容値を超える時刻ズレが継続する場合、売買判定を停止して安全側（見送り）へフォールバックする。

## セキュリティ境界

### 秘密情報

* APIキー・シークレット・認証トークンなどの秘密情報はソースコードおよびGit管理対象に含めない。
* 秘密情報は環境変数またはGit管理外の設定ファイルから注入する。

### APIキー

* APIキーは環境ごとに分離する（開発 / 検証 / 本番）。
* APIキーには最小権限を適用し、不要な権限を付与しない。
* ローテーション可能な運用手順を用意する。

### 出力マスキング

* ログ・コンソール・CSVなど外部出力に秘密情報を含めない。
* 例外メッセージやHTTPエラー詳細に機密値が含まれる場合はマスキングする。
* 少なくとも APIキー・シークレット・認証ヘッダは常にマスク対象とする。
